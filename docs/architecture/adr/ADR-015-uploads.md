# ADR-015：上传——multipart、取消与进度

状态：已接受（#193 的前置）。实现随 #193 落地，真机验证留 Phase 2。
日期：2026-11-23
关联：RFC-0001 §2.2/§2.3、ADR-011、ADR-013、ADR-014

## 背景

S12（#63）迁完消息域之后，`lib/http/msg.dart` 还剩三条，其中两条是上传：

| 接口 | 路径 | 调用点 |
|---|---|---|
| `MsgHttp.uploadImage` | `/x/upload/web/image` | 收藏夹封面（`fav_create/view.dart`） |
| `MsgHttp.uploadBfs` | `/x/dynamic/feed/draw/upload_bfs` | 动态配图、投票选项配图、私信图片（三处） |

它们没跟着 S12 走，不是因为「多几个请求构造函数」，而是要一项**传输层还
没有的能力**。ADR-013 决策一只给传输层定了 `Form` 与 `Json` 两种体，
`PostBody::Bytes` 是后来为 gRPC 加的——三种都是「一段已经在内存里的字节」。
multipart 不是：它要分段编码、要带 boundary，而且**不能整读进内存**，
一张 4K 截图十几 MB，低端机上会直接 OOM。

另外 `uploadBfs` 收一个 `CancelToken`，而 Rust 侧目前**没有任何「取消一个
进行中的请求」的通道**。

本 ADR 回答 issue #193 列的四个问题，外加一个它没问但必须一起定的（流式
读与大小上限）。

---

## 决策一：multipart 进 `WriteBody` 的第三个变体，体里放**文件引用**而不是字节

```rust
pub enum WriteBody {
    Form(Vec<(String, String)>),
    Json(serde_json::Value),
    /// multipart/form-data。普通字段照旧，文件只给一个**引用**。
    Multipart {
        fields: Vec<(String, String)>,
        file: UploadFile,
    },
}

pub struct UploadFile {
    /// 表单里的字段名。两条接口不一样：`uploadImage` 是 `file`，
    /// `uploadBfs` 是 `file_up`。给错服务端回 `code 0` 但没有 url。
    pub field: String,
    /// 本地文件路径。见决策二。
    pub path: String,
}
```

**考虑过但没选：让上传不走 `PreparedWrite`，单开一条路。**
`PreparedWrite` 的价值有三条，上传要其中两条：

- csrf 注入（ADR-013 决策四，全仓库唯一注入点）——两条上传都要带 `csrf`
  表单字段，单开一条路就会出现第二个注入点；
- 幂等定级进签名（决策二）——上传恰恰是最需要被看一眼的那种请求；
- 请求快照（决策六）——这一条**部分**要不到，见下。

所以复用，只在体上加一个变体。

**快照怎么办**：`PreparedWrite` 要能原样写进请求面快照，而文件内容显然不
能进快照。放**引用**而不是字节正好解决这件事——快照里记的是「这里有一个
文件，字段名 `file_up`，路径 `<...>`」，证明的是**请求形状**（字段名、
其余表单项、csrf 位置），而那正是 ADR-013 决策六要钉的东西。文件内容不是
请求形状的一部分。快照序列化时路径也**不原样写**，只记一个占位，否则
fixture 会带上作者机器的目录结构。

## 决策二：文件由 **Dart 给路径，Rust 自己开**

两个选项：路径字符串，或 Dart 读成字节再跨 FFI。

选路径。理由不是「省一次拷贝」（虽然确实省），而是**字节那条路把决策五的
流式读堵死了**：Dart 读成 `Uint8List` 的那一刻，十几 MB 已经在内存里了，
后面 Rust 再怎么流式也晚了。

代价是把文件系统权限问题推给 Rust。**这件事在本仓库是可接受的，但理由要
写清楚，别当成普遍结论**：

- Android 的 SAF uri（`content://...`）不是路径，Rust 开不了。但基线
  `MultipartFile.fromFile(path)` **同样开不了**——它要的也是真实路径。
  当前四个调用点的路径都来自 `image_picker` / `image_cropper`，这两个库
  都会先把选中的内容复制到应用缓存目录再给出真实路径。
- 所以这不是新增的约束，是把基线已有的约束写下来：**调用点必须先把内容
  落成一个真实文件**。将来若有调用点直接拿到 SAF uri，由它负责 materialize，
  不是由 Rust 去理解 uri scheme。

导出函数的文档里要写这一条，否则下一个人会以为 Rust 能收任意 uri。

## 决策三：取消沿用 ADR-014 的「id + 代际」注册表，不发明第二套

ADR-014 已经为直播长连接做过同一件事：`open` 同步返回单调递增的
`session_id`，宿主再带着它 `poll` / `close`，桥接层用一张注册表记代际，
过期的操作不影响其他代际，重复 `close` 成功。

上传照搬这个形状：

```rust
/// 同步返回，联网在共享 runtime 里做。连接还没建立也能取消。
pub fn upload_begin(...) -> i64;            // upload_id
pub async fn upload_await(upload_id: i64) -> UploadResult;
pub fn upload_cancel(upload_id: i64);
```

**为什么不用 FRB 的 `DropGuard` / `CancelableFuture`**：它们把取消绑在
Dart 侧对象的生命周期上，而这里的取消是**显式的用户动作**（退出发布页、
或者同批里另一张图失败了要把其余几张一起停掉）。绑生命周期会让「什么时候
真的停了」取决于 GC 时机，而那正是最难查的一类 bug。更要紧的是：本仓库
已经有一套取消机制在跑，第二套的代价不是多写几行，是以后每个人都要先问
「这里该用哪一套」。

**取消与重试的共存**（#193 担心的那条：取消过的请求绝不能被重试补发）
——**不需要新规则**。按决策四上传一律 `Idempotency::Unsafe`，而 ADR-013
决策一规定 `Unsafe` 的 `RetryPolicy` 是「一律不重试，`retry_count` 视为
0」。所以「取消之后被重试补发」在类型上就不成立。把它作为一条新规则写
下来反而有害：那会暗示其他档位可以重试被取消的请求。

取消的返回形状：已取消的上传以 `ErrorKind::Cancelled` 返回，与传输层既有
的取消分类一致（见 `HttpTransport::get` 的约定），宿主据此不弹 toast。

## 决策四：上传定级 `Unsafe`

按 ADR-013 决策三的三问：

1. 它是不是真的发请求？是。
2. 服务端语义是「置为」还是「加一次」？**加一次**——重复上传同一张图会在
   服务端多占一份存储。
3. 重发前查得到上一次生没生效吗？**查不到**。每次返回的 url 都不同，调用
   方无从判定上一次成没成。

→ `Unsafe`。这同时把决策三里「取消过的请求不能补发」自动做掉了。

**顺带记一笔**：`Unsafe` 在界面上的落地形态按 ADR-013 补充六是「让用户再
按一次」。发布页已经是这个形态（上传失败就整条发布失败，用户重新点发布），
不需要额外做什么。

## 决策五：流式读，并设一个显式上限

文件用 `reqwest::multipart::Part::stream_with_length` 加 `tokio::fs::File`
喂进去，**不整读**。

同时设一个上限并**在读之前用文件元数据判断**，超了直接返回
`ErrorKind::Protocol` 带明确文案，不要开始传了再失败：

- 单文件 **32 MiB**。取这个数不是因为服务端的限制（那个没有公开文档），
  而是「比任何一张手机截图或相机原图都宽裕，又不至于让一次失手选中的
  视频文件把流量跑光」。
- 这个上限是**客户端自己的护栏**，服务端自有它的限制且可能更严。所以超限
  的文案要说「本地限制」，别让用户以为是服务端拒绝的。

依赖变化：`reqwest` 要加 `multipart` 与 `stream` 两个 feature（当前
`rust/Cargo.toml` 里都没开）。

## 决策六：**不做**进度回调

issue #193 说「大概率还要上传进度回调（基线现在没有，但发布页有进度条的
需求）」。本 ADR **刻意不做**，理由有两条：

1. **基线没有进度。** 做了就不再是「迁移等价」，而是夹带一个新功能。
   ADR-011 决策五那套一次性对照会失去意义——没有基线可对。
2. **形状还定不下来。** 弹幕那条事件流是「一条长连接、持续产出」；上传是
   「每次上传一条、短命、要和 `upload_id` 对上」。照抄弹幕的形状会得到一
   个每个上传都要开关一次的流，而真正合适的大概是 ADR-014 那种**宿主轮询**
   （`upload_progress(upload_id) -> (sent, total)`），因为进度条本来就是按
   帧刷新的，不需要每个字节都跨桥。

真要做的时候按上面第二条的形状加，并且**单独开一张 issue**——它是一个
界面功能，不是迁移的一部分。写在这里是为了让下一个人知道这个选择是想过
的，不是忘了。

## 影响

- `WriteBody` 多一个变体，`transport_reqwest` 的两处 `match` 要跟着补
  （它们目前都是三分支的穷尽匹配，加变体会在编译期报出来，这是好事）。
- 桥接层多一张上传注册表，形状与 `live_socket` 的那张一致。
- `reqwest` 多两个 feature，二进制体积会涨一点；没有新的 crate 依赖。
- 迁完之后 `lib/http/msg.dart` 整个删除（`removeDynamic` 归 S5 续单 #150）。

## 刻意没做的

- **进度回调**（决策六）。
- **断点续传**。服务端没有相应接口，自己造一个只是多发一次请求。
- **多文件并发的调度**。发布页现在用 `Future.wait` 一次发四张，并发度由
  宿主决定；把它挪进 Rust 等于替调用点做了一个它更清楚的决定。
- **把 `removeDynamic` 一起迁**。它属动态域，归 #150，本片不动别的切片的
  文件（与 S12 当初留下它的理由一致）。
