# SPIKE-003 Windows 这一跑：人看出来的结论（issue #10）

配套的机器记录是 [2026-11-22-slint-ui-windows.md](2026-11-22-slint-ui-windows.md)，
实验台是 [`spikes/slint-ui`](../../../spikes/slint-ui)。那份由程序整份覆盖，
这份放它写不出来的东西：**哪些数曾经是假的、为什么假、以及 Phase 2 要据此
准备什么。**

本轮只覆盖 #10 范围的前四项（长列表 / 富文本 / IME / 无障碍），而且只在
Windows 上。**#10 不能据此关闭**，还差的在最后一节。

---

## 0. 先说最贵的那条：上一轮的滚动结论整段是假的

2026-11-21 那一轮记下的「虚拟化成立（两万行只实例化 7–12 个组件）」和
「滚动 p95 ~500ms、整体 7.5fps」，**两条都不是 Slint 的行为**，是同一个
bug 的两面：

```slint
// 错的
ListView { content-y: -root.scroll-y; }
// 对的
ListView { content-y <=> root.list-content-y; }
```

单向的声明式绑定会被**第一次命令式赋值永久摘掉**，而 `Flickable` 自己在
布局、滚轮、键盘时都会写 `content-y`。于是绑定在第一次布局之后就没了，
列表从此一动不动——

- 截图里永远是第 0 行（`02-list-scrolled` 和 `01-list-top` 逐像素一样）；
- 累计只实例化 7 行，看上去像**虚拟化效果极好**；
- `scroll-y` 不再被任何东西依赖，改它不触发重绘，于是帧间隔只剩 HUD 那条
  500ms 的节拍，看上去像**滚动极卡**。

三个现象互相印证，没有一个报错。查出来靠的是**看截图**——所有数都「自洽」，
只有画面不对。

> **Phase 2 记这一条**：Slint 里凡是「宿主侧要驱动、控件自己也会改」的
> 属性（滚动位置、选中项、展开状态、播放进度…）一律用 `<=>`。单向绑定在
> 这类属性上不会报错，只会在某个时刻悄悄失效。

修正之后的真实数字见下。

## 1. 长列表：过，而且余量很大

两万条真实形状的评论（走生产管线：pb → `project_main_list` → `ReplyEntity`
→ `reply_richtext::segment`），窗口 1470×930 物理像素、缩放 1.5：

| 项 | 数 |
|---|---|
| 匀速滚动（2400px/s，6 秒）单帧渲染 | p50 **0.7** / p95 **0.9** / 最慢 2.1 ms |
| 同一段的帧间隔 | p50 9.8 / p95 16.6 ms，长帧 2 次 |
| 一次跳到第 19999 行 | 最慢一帧 **8.4 ms** |
| 整段累计实例化的行组件 | **342** / 20000 |
| RSS | 建模型前 73 MiB → 峰值 265 MiB |

60Hz 一帧的预算是 16.7ms，滚动时只用掉 **0.9ms（p95）**。跳到两万行末尾
这种最坏情况也只有 8.4ms。**虚拟化与滚动不是 Phase 2 的风险点。**

两个需要注意的数，都不在 Slint 身上：

- **「生产分词」3.1 秒**。两万条走一遍 `reply_richtext::segment` 要 3.1s
  （约 0.15ms/条），这是 Rust 侧的代价，真机上不会一次性分两万条，但
  **分词必须离开 UI 线程**，否则一屏四十条就是 6ms，加上网络抖动很容易
  变成可感知的卡顿。
- **RSS 265 MiB**。两万条带配图结构的实体全驻留内存。真实产品不会一次装
  两万条，但这条数说明**模型侧的内存不是免费的**，分页/回收策略要在
  Phase 2 的设计里，不能指望 `ListView` 的虚拟化顺带解决——它只省组件，
  不省模型。

## 2. 富文本：行内样式过，行内图片**不行**

- `StyledText`（Slint 1.19 新增）能做行内颜色、链接、可选中，6 条解析
  0.12ms，全部成功。@某人 / #话题# / 链接 / 时间戳各有各的颜色。
- **行内图片直接不支持**，`StyledText::from_markdown` 原样报
  `Markdown images are not supported`。B 站评论里表情就是图文混排，
  Flutter 那边是 `WidgetSpan`。
- 于是实验台第三列是**自己排版**的：把 `segment` 的结果铺成 240 个
  绝对定位的 run。能做出来，但有一个硬伤——**Slint 不给文本测量 API**，
  断行只能按字号估字宽。中英混排、emoji、不同字重下这个估算必然失准。

> **Phase 2 的代价**：评论、动态、弹幕里的图文混排得自己写一个排版器，
> 而且得自己解决字宽测量（要么引 `rustybuzz`/`cosmic-text` 这类自己量，
> 要么把文本测量从 Slint 里挖出来）。这是本 spike 目前找到的**第一笔
> 确定会发生的额外工作量**。

## 3. 输入与焦点：全过

Tab 在三个 `LineEdit` 之间正常轮转（焦点序列 `[1, 2, 0, 3, 0]`，`0` 是失焦
上报），外部按键进得去，切到微软拼音打 `nihao` 能就地组字并上屏成「你好」。

**这一项第一次跑出来是 FAIL，而且 FAIL 得很有说服力**：焦点序列空的、
三串字母全挤在第一个框里、还少了一个字符。原因不在 Slint，在实验台自己：
`drive.ps1` 切到中文输入法之后**从不切回来**，输入法状态跨进程、跨次运行
地留着，于是**下一轮**的「英文直接输入」是在中文输入法里打的——`abc` 上屏
成 `ABC`、`def` 上屏成「得分」。单跑一轮永远看不见，连着跑两轮才出现。

现在脚本在英文那一段之前显式切回 `00000409`。

## 4. 无障碍：Windows 这一侧能读，但这只是三分之一

UIA 树里：列表是 `List`，可见行是 `ListItem` 且各自带名字，`IsOffscreen`
全 false；一行读出来是「长江七号0 说：前排。赞 0，回复 0」而不是七八个
零碎文本；`accessible-label` 盖得过控件自己的文本（按钮上写着「点赞 1024」，
读出来是「点赞，当前 1024」）；按钮 / 勾选框 / 滑块 / 输入框各自带角色、
名字，滑块的取值读得出 `30（0..100）`。

两条限制必须一起写进结论：

1. **这是 UIA，不是读屏软件实读。** 树里有的东西，各家读屏怎么念还有差别；
   macOS 的 VoiceOver 和 Android 的 TalkBack 走的是另外两套 API，**都没验**
   （mac 卡在 #8，Android 要真机）。
2. **滑块取值一开始也是空的**，差点被记成「Slint 没把值暴露出去」。实际是
   `uia-dump.ps1` 只问了 `ValuePattern`，而滑块走 `RangeValuePattern`。
   无障碍结论最容易这样被工具自己做坏：**问错了 pattern，和控件没实现，
   在记录里长得一模一样。**

## 5. 实验台这一侧踩的坑（下一个人省得再踩）

| 坑 | 症状 | 真因 |
|---|---|---|
| `win/*.ps1` 无 BOM | 按键 / IME / UIA **全 FAIL**，像 Slint 收不到输入 | `powershell.exe` 5.1 按 ANSI 代码页读无 BOM 文件，中文注释拆成半个字符，解析阶段就挂；报的却是正常行「缺少表达式」 |
| UIA 的 JSON **带** BOM | `expected value at line 1 column 1` | `[Text.Encoding]::UTF8` 这个现成实例带 BOM。源码要 BOM、JSON 不要，方向正好相反 |
| 输入法不复位 | 下一轮的英文输入变成中文 | 见 §3。跨进程、跨次运行留存 |
| `cargo test` 不刷新 `target/release/<bin>.exe` | 整整一轮跑的是旧二进制，改的脚本没生效 | `cargo test` 建的是测试壳。跑实验前一律 `cargo build --release` |
| `cmd /c ver` 取系统版本 | **乱码进了提交的记录**（`[?汾 10.0.26300]`） | 控制台输出走 OEM 代码页。改用 sysinfo 走系统 API |
| 只量帧间隔 | 空闲时不重绘被记成 500ms 长帧 | 见下 |

**最后一条值得单独说**：原来的 `FrameMeter` 量的是两帧之间的**间隔**，
它把「这一帧画得慢」和「这一帧根本没画」混成同一个数。界面没变时不重绘是
渲染器的正确行为，但在报告里读起来是「Slint 卡了半秒」。现在每个分段写
两组数——渲染耗时（`BeforeRendering`→`AfterRendering`）和帧间隔——外加
16ms 定时器的次数做对照。**结论只看渲染耗时。**

查这件事时还顺手做了个对照程序 `frame-floor`：同样的窗口、同样的
`ListView`、每帧只动 `content-y`，量这台机器上 Slint 的呈现上限。它给出
425 帧 / 425 次 tick、58fps、每次属性变更都换来一帧——**正是它把「这台机器
限频」排除掉，才逼出了 §0 那个绑定 bug。**

## 6. #10 还差什么

- **34 个补丁逐项评估**（#10 的评论里提的那半边，范围比这里大）：
  `lib/scripts/*.patch` 代表上游 Flutter 满足不了、作者改了框架才做出来的
  交互——底部弹窗手势、TabBar 指示器、可拖拽面板、文本选择、滚动边界与
  手势识别。换 Slint 后这些不会自动存在。要逐个读 diff、归成「Slint 原生
  支持 / 需自行实现 / 做不到」三档。**做不到的直接计入 Phase 2 No-Go。**
  本轮没动。
- **触控手势 / 惯性 / 下拉刷新**：这台机器没有触摸屏。触摸分发本身已在
  SPIKE-002（#9）的真机上验过，但惯性与下拉刷新属于上面那半边。
- **VoiceOver（mac，#8）与 TalkBack（Android 真机）实读**。
- **其他平台**：本轮只有 Windows。macOS 与 Android 上 Slint 的
  `ListView` / `StyledText` / IME 行为要各自再跑一遍——IME 这一项尤其，
  三个平台是三套机制。
