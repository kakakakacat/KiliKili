## 1. 旁白实读

不是人边听边记的：用 AppleScript 控制旁白，System Events 发真实的 VO 键，
每一步读回旁白的 `last phrase`（它刚念的话）和 `text under cursor`。脚本在
[`spikes/slint-ui/mac/vo-drive.sh`](../../../spikes/slint-ui/mac/vo-drive.sh)，
跑之前要开的四个开关写在脚本开头——少一个都是静默失败，看着像「旁白什么都没念」。

下面引号里是旁白**原样念出的文本**。

### 1.1 控件页：全部 PASS

| 操作 | 旁白念的 | 判定 |
|---|---|---|
| 走到按钮 | 「点赞，当前 1024 button」 | PASS：念的是 `accessible-label`，不是按钮上写的「点赞 1024」 |
| 走到勾选框 | 「只看楼主 未勾选 checkbox」 | PASS |
| VO+空格 | 「已勾选 只看楼主 checkbox」，再按一次「未勾选 …」 | PASS：状态变化会播报 |
| 走到滑块 | 「30% 播放进度 slider」 | PASS |
| 进入滑块后按 → | 「31%」 | PASS：调值会播报 |
| 走到输入框 | 「搜索评论 text field」 | PASS |
| 激活后打 `abc` | 「ABC AA，BB，CC」，AX 树里取值是 `abc` | PASS（逐字回显是旁白的正常行为） |

一处没弄明白、不影响判定：打完字之后光标下的文本是「ABC **已选择** AA，BB，CC」，
像是 Slint 把选区报成了整段。要查得看 `AXSelectedTextRange`，本轮没做。

### 1.2 长列表：一行读得对，但读不到第 8 行以后

| 操作 | 旁白念的 |
|---|---|
| 走到列表 | 「评论列表 list」 |
| 进入列表 | 「长江七号0 说：前排。赞 0，回复 0 （1/7）」 |
| 往右 ×6 | 逐条念到「路过的6 说：笑死 😂 这波操作 I can't believe it 🎉 BGM 是 Lost River 吧。赞 2514，回复 30 （7/7）」 |
| 再往右 | 原地重复第 7 条 |
| VO+Fn+↓（翻页） | 什么也没念，列表没动 |

三件事：

1. **一行念成一句话，PASS。** 每行在 AX 树里底下还挂着昵称、等级、正文、赞、回复
   五段文本（带图的那行还有四个「图」），但旁白把行当成叶子，不会再逐段念一遍。
   Windows 记录里标「人工确认」的那一项，在 macOS 上可以判 PASS。
2. **总数是错的：「（1/7）」而不是 1/20000。** 列表只把实例化了的行放进 AX 树，
   旁白据此数出 7 条。Windows 的 UIA 树也是 7 个 ListItem，同一个原因，只是那边
   没有屏幕阅读器去念它。
3. **走不出第一屏。** VO+→ 到第 7 条就停，翻页滚动没有反应——`ListView` 没有
   把滚动动作暴露给无障碍。用鼠标滚动当然能看到后面的行，但用旁白的人不会这么做。

第 2、3 条是同一个问题：**Slint 的 `ListView` 的虚拟化对无障碍不透明。**
Phase 2 要么上游补（AccessKit 的节点有「集合大小 / 在集合中的位置」和滚动
动作，缺的是 Slint 这边接上——没核对 Slint 源码，是推断），要么自己在列表外面包一层「当前第几条 / 共几条」
加上焦点到边缘时主动滚动——后者是应用层能做的，但每个长列表都得做。
建议并进 #192 一起跟（那张单子本来就是「上游补无障碍之后重验」）。

### 1.3 刚启动时拿到的是占位树

AccessKit 在 macOS 上是懒初始化的：第一次查询只拿到一个没有角色、没有子节点的
空元素，约 1.5 秒后才是完整的树。Android 上游那份实测里也写着「服务刚连上时拿到
占位树」，是同一件事。对用户的影响是：窗口刚打开就开始按 VO 键，前一两下可能是空的。
`ax-dump` 默认抓两轮就是为了不被这个骗。

## 2. 只在 macOS 上出现的：固定宽度的子元素会钉死窗口最大宽度

第一轮跑完，「全屏」截图只有 445 逻辑像素宽，窗口也拉不宽。原因：

- 控件页里有一个 `Slider { width: 240px; }`；
- Slint 的布局把子元素的最大宽度往上传，于是整个场景的 max-width 被钉在 445；
- Slint 把根布局的约束设成窗口的约束，**macOS（winit）把它当硬上限**——
  拖不宽，全屏也只有这么宽；Windows 那一轮在同一个场景下缩放到 980 是正常的。

在外面包一层 `HorizontalLayout { alignment: start; }` 之后约束不再往上传，
窗口恢复正常（这是本轮唯一一处 UI 改动）。富文本页那三列也是固定宽度，窗口最宽
1188，**这一处故意没改**：列宽要和 Windows 那一轮逐列对照。

> **Phase 2 记这一条**：根布局里任何一个固定宽/高的子元素，都可能在 macOS 上变成
> 窗口的尺寸上限，而 Windows 上看不出来。固定尺寸的控件要包一层不设上限的布局。

## 3. 为什么 Tab / 输入 / IME / 最小化是 NOT TESTED

这四项要从窗口**外面**发按键、切输入法，Windows 用的是 `win/drive.ps1`。macOS
这边还没写对应的驱动，本轮按 `--no-driver` 跑。旁白那套脚本（System Events 发键）
证明了外部按键这条路在 macOS 上走得通，写一个 `mac/drive.sh` 不难；中文 IME 要用
`TISSelectInputSource` 切输入源，是其中最麻烦的。要不要补，等仓库所有者定。

记录里「VoiceOver / TalkBack」那一行仍写着 NOT TESTED，那是实验台的固定文案，
实读结果以本文 §1 为准。

## 4. 实验台自己的一个问题：「缩放后」那张截图截的是全屏

`07-resized` 是 3024x1898（全屏尺寸），不是 980x620。截图排在「下一次重绘」时做，
而这一页是静止的，缩放之后没有立刻重绘，下一帧要到切全屏时才画——于是截到的是
全屏之后的画面。缩放本身生效了：退出全屏后窗口回到 980x620（`09-back-to-list`，
以及记录里的「窗口」一行）。Windows 那边没撞上，是因为那边的缩放会立刻触发重绘。
改法是截图时主动请求一次重绘，没在本轮做。
