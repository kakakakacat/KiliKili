# #219 插帧接入：正式 crate、档位与回退、移动端真机

日期 2026-11-24；第二轮 2026-11-26（倍速、源帧率、Anime4K、回退的一个漏洞，§6）。父 issue #211，算法与原型在 #218
（[`2026-11-24-interp-218.md`](2026-11-24-interp-218.md)）。

## 0. 范围与结论

**范围调整（已与仓库所有者确认）**：#219 写的是「接到 Slint 客户端的播放器里」，但仓库里
还没有 Slint 客户端（RFC §4 的 `app-slint` 未建），也没有正式的 `NativeMpvAdapter`。
所以这一轮把插帧提成**正式 crate** `rust/crates/player-interp`，档位、回退、生命周期、
音画延迟都在里面，带单测、进 CI；刷新率请求与温控这些平台胶水接在两个实验台上
（`spikes/slint-mpv` 的 Android 入口、`spikes/slint-ios`），用实验台做真机验收。
`app-slint` 建好后，宿主照 `player_interp::engine` 模块文档里的样板接上即可。

结论：

1. **接入形态成立。** 宿主每个渲染回调调 `begin_vsync` → 直通或插帧 → `end_vsync`，
   mpv 部分留在宿主，crate 不依赖 libmpv、Slint 或平台 SDK（§1）。
2. **Adreno 610（SM6225）上正式路径稳定在 59–60 FPS**：30→60、24→60、24 一拍二→60 都是；
   45 档在 60 Hz 屏上按规则落到 30 或直通（§3.1）。
3. **iPhone 16 Pro Max 上 30→60、24→60 稳定 60 FPS；「跟随」放开到 120 后 30→120、
   24→120 稳定 120 FPS**（§3.2）。这是 #219 要的高刷数据，但只有这一台，「跟随」的上限
   **仍保持 60**，等 Android 旗舰的 90 / 120 Hz 结果。
4. 验收中发现并修掉了 7 个问题，其中 3 个只在真机上出现（§4）。最值得记住的两条：
   iPhone 要 45 Hz 时系统在 40 / 48 Hz 间逐帧交替；这台 SM6225 工程板 skin 40 ℃ 就报 SEVERE。
5. 连续 15 分钟两台都没有降档、没有温控介入（§3.3）。
6. 还没做的验收项列在 §5，#219 保持打开。
7. **第二轮（§6）**：倍速接上了，三端每次改倍速 `audio-delay` 只改一次；源帧率改以 mpv 的
   `container-fps` 为准（测量兜底），开播与拖动不再中途改 `audio-delay`；Anime4K 改成按窗口
   放大的槽之后在插帧路径下生效，iPhone 16 Pro Max 上 S 档 + 插帧稳定 60 FPS，Adreno 610 连
   Anime4K 本身都跑不动；修掉一个回退永远不触发的漏洞（一秒只有三帧的窗口被当成「样本不够」）。

## 1. `player-interp` 的结构

| 模块 | 内容 | 与 GL 有关 |
|---|---|---|
| `policy` | 设置（关闭 / 45 / 60 / 跟随）+ 片源帧率 + 屏幕刷新率 → 档位 | 否 |
| `governor` | 持续掉帧、补帧超时、温控 → 降档；稳定后升档，失败退避 | 否 |
| `refresh` | 平台读数去抖；没有平台读数时按回调间隔测刷新率 | 否 |
| `sched` | 源帧环、选帧、`target_time` 单位换算（#218） | 否 |
| `controller` | 串起上面四样，处理生命周期事件与 `audio-delay` | 否 |
| `gpu` / `shaders` | GLSL 块匹配与合成（#218，原样搬来） | 是 |
| `engine` | `Interpolator`：控制面 + GPU，给宿主渲染回调用 | 是 |

CI（`rust.yml`）跑前五个模块的 57 个单测；GPU 一半只能在实验台和真机上验
（VALIDATION-CAPABILITY §3.1 已注明）。

### 1.1 档位规则

**只做能均匀呈现的帧率**：输出帧率必须是屏幕刷新率的整数分之一（每 k 个 vsync 出一张新帧）。
「目标」是上限，实际取刷新率约数里不超过它的最大一个，并且要比片源高 5 % 以上：

| 屏幕 | 设置 | 片源 30 | 片源 24 |
|---|---|---|---|
| 60 Hz | 60 | 60（k=1） | 60（k=1） |
| 60 Hz | 45 | 直通（屏幕无法均匀呈现） | 30（k=2） |
| 90 Hz | 45 | 45（k=2） | 45（k=2） |
| 90 Hz | 跟随（上限 60） | 45（k=2） | 45（k=2） |
| 120 Hz | 60 / 跟随（上限 60） | 60（k=2） | 60（k=2） |
| 120 Hz | 跟随（上限 120） | 120（k=1） | 120（k=1） |

降档就是在这张约数表里往后挪：120 Hz、24 fps 片源、上限 120 时是 120 → 60 → 40 → 30 → 直通。

请求帧率：Android 按设置请求**内容帧率**（45 / 60，`FIXED_SOURCE`），系统挑整数倍的模式；
「跟随」不请求。iOS 的 ProMotion 没有「系统默认」可跟，display link 必须给一个速率：
45 / 60 照请求，「跟随」与关闭请求 `min(屏幕最高, 上限)`（`Setting::display_link_rate`）。

### 1.2 回退

一秒一个窗口：掉帧（间隔 > 1.5 个周期）+ 补帧超时（插帧段 CPU > 1 个周期）占比超过 10 %
算坏窗口，连续两个降一档；在一档上稳定 30 秒后试着升一档，升上去 10 秒内又被降下来就把
等待翻倍（上限 5 分钟）。温控 Severe 及以上回到原帧率，Moderate 禁止升档。

### 1.3 生命周期与音画延迟

| 事件 | 处理 |
|---|---|
| 拖动 | 下一张源帧到来时清环（不立刻清，免得黑一两帧） |
| 切集 / 切清晰度 | 清环并清源帧率样本，重新判档 |
| 前后台 | 后台直通；回前台同拖动 |
| 画中画 | 直通（原帧率）；退出同拖动 |
| 渲染上下文重建 | 清环，GPU 侧重建 |

`audio-delay` = 两个源帧间隔（跳重复帧要多前瞻一张）+ 15 ms；直通时 0。宿主**异步**写给 mpv。
30 fps 片源约 81 ms，24 fps 约 98 ms。什么时候改见 §6.2（第一版是「变化超过 10 % 才改」）。
倍速下 `audio-delay` 要乘倍速（§6.1）。

## 2. 设备与跑法

- **Android**：SM6225 / Adreno 610，Android 14，640×960、60 Hz 单一模式，`hwdec=mediacodec`。
  与 #210 补测、#218 是同一台（工程板 `DN_ENG41`）。全程接电源。
- **iOS**：iPhone 16 Pro Max（A18 Pro），iOS 27.3，gl 模式（mpv GLES → IOSurface → Metal → Slint）。
- **macOS**：Apple M4，ProMotion 内屏（只用来先跑一遍状态机，见 §4 第 4 条）。
- 素材同 #218：BBB 30 fps / 24 fps / 24 fps 一拍二，720p。

```sh
# Android（构建同 spikes/slint-mpv/README.md）
./interp-android.sh -- --video bbb30.mp4 --setting 60 --flip-y --hwdec mediacodec \
    --duration 40 --seek-to 5 --event-at 0:thermal-nominal --event-at 10:seek \
    --event-at 15:pip --event-at 18:pipexit --record e60-30.md
# iOS（env.json 见 spikes/slint-ios/README.md）
{"SPIKE_VIDEO":"~/Documents/bbb30.mp4","SPIKE_INTERP_SETTING":"follow","SPIKE_INTERP_FOLLOW_CAP":"120","SPIKE_PIP":"0"}
```

## 3. 真机结果

### 3.1 Android（Adreno 610，60 Hz）

| 组 | 档位 | 当前 FPS（稳态） | 显示间隔 p50 / p95 | 插帧段 CPU p50 / p95 | `audio-delay` |
|---|---|---|---|---|---|
| 30 fps，60 档 | Interp 60（k=1） | 59–60 | 16.60 / 22.65 ms | 1.95 / 8.27 ms | 84 ms |
| 24 fps，60 档 | Interp 60（k=1） | 60 | 16.58 / 23.05 ms | — | 102 ms |
| 24 一拍二，60 档 | Interp 60（k=1） | 57–60 | 16.68 / 22.71 ms | — | 102 ms |
| 24 fps，45 档 | Interp 30（k=2） | 29–31 | 16.67 / 22.64 ms | — | 102 ms |
| 30 fps，45 档 | 直通（屏幕无法均匀呈现） | 30 | 16.66 / 22.32 ms | — | 0 |

- 刷新率来自 Choreographer 回调（60.000004 Hz），`ANativeWindow_setFrameRate(60, FIXED_SOURCE)`
  返回 0。这台屏幕只有一个模式，所以**模式切换本身没测到**（要旗舰机）。
- 30→60 那组 40 秒里注入了拖动、PiP 进出：拖动后那一秒 27 FPS、下一秒 49、之后 60；
  PiP 期间直通 30 FPS、`audio-delay` 0，退出后约 1 秒回到 60。40 秒内没有误降档，
  mpv `frame-drop-count` 1。
- 选帧：「环还空、照直通画」（`Presented::Nothing`）每组 1–2 次，都在开播或切换的那一帧，
  没有黑帧。
- 连续 15 分钟：见 §3.3。

**温控**：这台工程板 skin 传感器的 SEVERE 阈值是 **40 ℃**（`dumpsys thermalservice` 的
`mHotThrottlingThresholds`）。第一轮开跑时机身刚被前面几轮测试捂热（skin 40.6 ℃），平台报
`Thermal Status: 3`，正式路径按规则整轮走「直通（温控）」。上表各组都用
`--event-at 0:thermal-nominal` 覆盖了温控，测的是插帧本身；§3.3 的 15 分钟那组同时记了平台
读数，凉下来之后全程 Nominal，插帧 15 分钟也没把 skin 推过 37.2 ℃。**「Severe 回原帧率」
这条规则要在零售机上再确认一次**：阈值低的机型上，连续看几集之后插帧可能就一直是关的。

出帧改由 CADisplayLink 驱动（#218 用 8 ms 定时器，一半输出白算），刷新率取 display link 的

## 4. 验收中发现并修掉的问题

1. **补帧超时的阈值太紧**（macOS）：第一版按「插帧段 CPU > 0.75 个周期」算超时，120 Hz 上
   3.7 秒就降档，而显示间隔 p99 只有 13.8 ms。运动估计每对源帧做一次，那一帧 CPU 高但 GPU 是
   异步的，不一定误 vsync。改成「> 1 个周期」（注定赶不上）。
2. **源帧率样本太少**（macOS）：4 个间隔就下结论，开播头 0.5 秒估计在 29.4–30 之间抖，
   `audio-delay` 改了 5 次。改成 8 个，延迟只在变化超过 10 % 时改。
3. **输出帧率的统计窗口跨过了直通期**：PiP 退出后第一秒报「当前 9 FPS」。切换时清零。
4. **VRR 屏幕上测刷新率**（macOS ProMotion）：间隔的指数平均落在 64–87 Hz，出了 37.67 fps 的
   档位。改成中位数 + 只认常见刷新率 + 连续稳定 30 帧才采纳。**但 macOS 上 Slint 的回调本身不
   锁 vsync**（间隔中位数 13.4 ms ≈ 75 Hz），「刷新率约数」的前提不成立——这是桌面端 #220
   要解决的（CVDisplayLink 驱动，或平台报刷新率），实验台先用 `--display-hz` 顶着。
5. **iOS display link 的范围给宽了**：第一版请求 `(preferred/2, preferred)`，系统时常挑 40 Hz，
   刷新率在 40 / 60 间跳，回退控制器把 40 Hz 的间隔当成掉帧、降到直通。改成上下限都钉死。
6. **平台读数也要去抖**（iOS）：要 45 Hz 时系统在 40 / 48 间逐帧交替，48 那几帧判「屏幕无法均匀
   呈现 45」→ 直通，`audio-delay` 每零点几秒在 0 与 98 ms 间来回切。平台读数改为同样的「连续
   30 帧才采纳」。
7. **SM6225 工程板 skin 40 ℃ 就判 SEVERE**：不是代码问题，但它决定了「温控」那条规则在这台
   机器上的实际效果，见 §3.1。

## 6. 第二轮（2026-11-26）

在最新 main 上接着做 §5 里不需要额外设备的几项。macOS 的数字都用 `--display-hz 60`
（§4 第 4 条）。

### 6.1 倍速

倍速改变源帧在墙钟上的间隔（`target_time` 是墙钟），而 mpv 的 `audio-delay` 加在 pts 上、
是**媒体时间**：2 倍速下 0.1 s 的 `audio-delay` 在墙钟上只有 50 ms。所以：

- 宿主观察到倍速变化时调 `Interpolator::set_speed`；
- 档位按墙钟上的源帧率判（24 fps 的 1.25 倍 = 30，2 倍 = 48）；
- `take_av_delay_change` 返回**媒体时间**（墙钟延迟 × 倍速）；
- 改倍速等同一次拖动（下一张源帧到来时清环），并清掉回退的降档记录（§6.4）。

三端都按「1 → 1.25 → 2 → 1 倍速、再拖动一次」跑，`audio-delay` 序列（ms）：

| 片源 | macOS | Adreno 610 | iPhone 16 Pro Max |
|---|---|---|---|
| 24 fps | 98 → 102 → 113 → 98 | 98 → 102 → 113 → 降档 0 → 98 | 98 → 102 → 113 → 98 |
| 30 fps | 81 → 85 → 0（60 fps ≥ 屏幕，直通）→ 81 | 81 → 85 → 0 → 81 | 81 → 85 → 0 → 81 |
| 24 一拍二 | 98 → 102 → 113 → 98 | 98 → 102 → 113 → 降档 0 → 98 | — |

每次改倍速只改一次（中间那个「→ 0」是插帧 ↔ 直通的切换）；拖动不改。Adreno 610 上 24 fps
的 2 倍速（墙钟 48 → 60）补不过来，回退降到直通，这是预期的；回到 1 倍速后回到 60 档。
iPhone 上全程 59.5–60.8 FPS。

### 6.2 源帧率：以 `container-fps` 为准

第一版按 `target_time` 间隔测源帧率。两个现象说明只靠测量不够：

- 中位数落在哪一个带抖动的样本上就是哪个，30 fps 片源报 28.7（单测里复现）。改成「丢掉离中位数
  超过 25 % 的间隔再取均值」，并吸附到「常见片源帧率 × 倍速」（12 / 15 / 24 / 25 / 30 / 48 /
  50 / 60，±3 %；23.976 / 29.97 并进整数档——这个值只定档位与延迟，每张输出帧插在哪里按源帧
  自己的 `target_time`）。
- **起播头一秒 mpv 在追帧**，`target_time` 稳定地偏：iPhone 上 24 fps 片源依次报 26.7、25、24，
  30 fps 报 33.3 再 30，`audio-delay` 开播时连改三次。这不是抖动，去抖与滞回都挡不住。

所以改成以 mpv 的 `container-fps`（媒体时间）× 倍速为准：宿主在渲染线程以外读（桌面 /
Android 在读视频尺寸的后台线程里，iOS 在每 30 帧读一次视频尺寸的地方），交给
`set_source_fps_hint`。测量照旧跑，只有它已经稳定、又与 `container-fps` 差出 15 % 以上
（VFR、容器标错）时才信测量。测量路径本身也加了：起播头 4 个间隔不记、改倍速后头 3 个不记且
要攒满一整窗、新估计连续 6 张源帧不变才采纳。

`audio-delay` 什么时候改：插帧 ↔ 直通立刻改；倍速、换片源这种宿主告知的变化立刻改；其余（估计
变了）吸附上常见帧率的要连续 30 个 vsync 都是新值才改，吸附不上的（VFR）仍按 10 % 滞回。

结果：macOS 三个片源各两轮、Adreno 610 三个片源、iPhone 两个片源，开播都只设一次
`audio-delay`（macOS / Android 在开播 0.15–0.3 s）；改倍速后不再先直通 0.7 秒等样本。
拖动后的那一秒「当前」会掉到 12–24 FPS（Android 硬解 seek 停顿约 0.7 秒，统计窗口跨过了它），
下一秒回到 59–60，与第一轮相同。

### 6.3 与 Anime4K 叠加

**问题**：mpv 的着色器作用在 mpv 画进槽的那一步。槽是视频原始尺寸时，mpv 的输出不比输入大，
Anime4K 放大档的条件（`OUTPUT.w > HOOKED.w`）不成立，等于没开。**iOS 实验台连直通也一样**：
零拷贝的 IOSurface 目标是视频原始尺寸、由 Slint 缩放。

**做法**：`player_interp::engine::slot_size(视频, 窗口, 放大着色器?, 像素上限)`——开了放大类
着色器时，槽（iOS 上连同零拷贝目标）改成视频按比例放进窗口后的尺寸，只放大不缩小，不超过宿主
给的像素上限。mpv 在槽里做完放大，插帧在放大后的画面上做，输出 pass 1:1 贴上去。代价：运动估计
的像素按放大倍数平方涨；搜索半径按槽像素算，放大 2 倍时能跟上的源像素位移减半。

**macOS**（720p → 1920×1050 窗口）：截图对比，源尺寸槽 + Anime4K 与没开 Anime4K 一样软，放大槽
+ Anime4K 与直通 + Anime4K 一样锐。

**Adreno 610**（270p 片源 → 640×360 槽，Anime4K Mode A = Clamp + Restore_M + Upscale_M ×2 +
Upscale_S）：

| 配置 | 显示间隔 p50 | 结果 |
|---|---|---|
| 直通，无着色器 | 16.7 ms | 30 FPS |
| 直通 + Mode A | 40.7 ms | **mpv 丢 120 帧**，跟不上 30 fps 片源 |
| 直通 + Restore_S / Upscale_S | 36.7 ms | 丢 55 帧 |
| 60 档，无着色器 | 16.7 ms | 60 FPS |
| 60 档 + Mode A，源尺寸槽 | 36.7 ms | 回退到直通（Anime4K 没生效） |
| 60 档 + Mode A，放大槽 | 319 ms | **卡在 3 FPS 不回退** → 修了（§6.4），修后 3 秒内回到直通 |

低端机连 Anime4K 本身都跑不动，与插帧叠加无从谈起。

**iPhone 16 Pro Max**（270p 片源 → 1320×742 槽）：

| 配置 | 视频 / UI fps | 结果 |
|---|---|---|
| 60 档，无着色器，放大槽 | 60 / 118 | 正常 |
| 直通 + Mode A | 30 / ~80 | 跟得上 30 fps 片源，UI 从 120 掉到 80 |
| 60 档 + Mode A，源尺寸槽 | 60 / ~90 | 60 FPS，但 Anime4K 没生效 |
| 60 档 + Mode A，放大槽 | 30 / ~83 | 叠加太重，回退到直通 |
| 60 档 + Restore_S / Upscale_S，放大槽 | **60 / ~100** | 稳定 60 FPS，出帧 p95 3.6 ms |

**产品决定（2026-11-26，仓库所有者）：不替用户决定，也不按机型分档。** 插帧、Anime4K 各档
在所有设备上都作为选项提供，开关由用户自己决定；设置页要把风险说清楚，依据就是上面两张表：

- Anime4K 本身吃 GPU：低端机（实测 Adreno 610）开了就丢帧，直通也一样；高端机（iPhone 16
  Pro Max）Mode A 能跟上 30 fps 片源，但界面从 120 掉到约 80 FPS。
- 与插帧同时开更重：iPhone 上 S 档 + 插帧稳定 60，Mode A + 插帧跟不上；开播后插帧会因持续
  掉帧自动退回原帧率（#219 的回退规则），Anime4K 不会被自动关掉或降档。
- 都会更耗电、更热（功耗还没量，§5）。

所以**不做**「Anime4K 跑不动时自动降档 / 关掉」。按机型的「高端 / 低端」判断也不做：能不能
同时开取决于片源分辨率、屏幕尺寸、帧率与发热，不是机型的固定属性。风险提示的文案在宿主，
接入 `app-slint` 时写。

### 6.4 回退的两个漏洞

1. **一秒只有几帧时永不降档。** 回退按一秒一个窗口判，帧数不到 10 的窗口当「样本不够」跳过
   （本意是暂停时宿主不重画）。Adreno 610 上 Anime4K + 放大槽每帧 300 ms，一秒三帧，每个窗口
   都被跳过，卡在 3 FPS。改成：帧数不够、但至少两帧且一半以上**补帧超时**（我们自己的耗时超过
   显示周期）的窗口照样算坏窗口——暂停重画不会让耗时变长，不会误伤。
2. **改倍速后停在降过的档上。** 24 fps 2 倍速把 Adreno 610 压到降档，回到 1 倍速后停在 24 → 30
   那一档，要等 30 秒升档才回 60。改倍速、换片源时清掉降档记录与退避（温控保留）。

### 6.5 音画同步：素材与量法备好了，差一次录像

`spikes/slint-mpv/avsync.py`：`make` 生成每秒一次「整屏白一帧 + 1 kHz 哔声 40 ms」的素材（24 / 30
fps 各一份已经放进 Android 板与 iPhone 实验台的数据目录），`measure` 从录像里取每次闪光的亮度
质心与哔声起点，打印声 − 画偏差。拿素材本身自检是 +0.1 ms。

没测成的原因：要把屏幕与声音录在同一个时钟上。这台 Mac 没有回环声卡，用麦克风录扬声器会在
房间里响一分钟哔声；把 USB 连着的 iPhone 当成 AVFoundation 的「屏幕 + 声音」源（QuickTime 的
做法，同一时钟）要摄像头权限，本进程还没有，申请会弹系统对话框。需要人做的一步：iPhone 上
系统录屏（带声音）播 `avsync30.mp4`，`60` 档与 `off` 各录一段，对两段的中位数做差，应 ≤ 一帧。
