## 0. 决策四那个组合：先说结论

ADR-016 决策四定的是「模糊优先用原生 `backdrop-blur`，自绘只负责折射与高光」，
理由是代价：原生模糊 0.65 ms，自绘模糊 1.71 ms。ADR 里留了一条未验项：

> 自绘那层采到的背板里已经含有原生那层画的渐变与描边，**折射会把描边一起
> 抹开**。这是要看画面才能判的事。

**答案是：会，但那只是其中一种摆法。** 决策四没有说清「渐变与描边归谁画」，
而这一项决定成败：

| 摆法 | 原生那层画什么 | 自绘那层画什么 | 结果 |
|---|---|---|---|
| `over-full`（读法甲） | 模糊 + 渐变 + 1px 白描边 | 折射 + Fresnel + 高光 | ❌ **描边被折射拖出第二道** |
| `over-blur`（读法乙） | **只有模糊**（透明、无描边、无阴影） | 折射 + Fresnel + 高光 + 渐变 + 描边 | ✅ 干净 |

读法乙里自绘层采到的背板**没有描边可抹**——描边由它自己在折射之后画。
于是决策四成立，只要把它写清楚：**原生那条只开 `backdrop-blur`，材质层整个
归自绘。**

**这张表的判据只在 Windows / FemtoVG 上量过**（§1 那组剖面，scale 1.5）。
Android 上只跑了读法乙——也就是可用的那一种，画面与桌面一致。读法甲在
Android 上没跑：它已经被判掉了，再跑一次只是多一张同样的坏图。
两个后端走的是同一条 `NativeOpenGL` 路径、同一份 GLSL，所以这条结论按
「与后端无关」理解；要是哪天发现不是，先怀疑这一句。

## 1. 判据：过胶囊左端圆头的一行亮度剖面

形状对不齐、抗锯齿、亮度微差这些肉眼都不可靠，所以判据取一行像素：过胶囊
垂直中心、横穿左端圆头，`x=344..383`（物理像素，scale 1.5）。
描边被抹开的话这一行上会出现**两个**亮峰。

```
原生 only ：75 75 75 75 74 74 74 74 115 158 104 105 105 107 107 ...
                                            ^^^ 一个峰，之后平着走
over-full ：75 75 75 75 74 74 74 74 117 149 144 140 134 127 120 114 151 138 128 126 ...
                                            ^^^ 峰 1            ^^^ 峰 2（内移 7 物理px）
over-blur ：76 76 76 76 76 76 76 76  74 177 179 159 155 149 144 140 133 127 124 120 ...
                                            ^^^ 一个峰，单调下降
```

峰 2 距峰 1 **7 物理像素 ≈ 4.7 逻辑像素**，和 `refraction_strength = 7`
（逻辑像素，乘上 `rim` 的衰减）对得上——它就是那道白描边被沿法线推进来的
那一份。

截图（`shots/p2-over-full.png` / `p2-over-blur.png`，按 §7 复跑）里肉眼也看得出
`over-full` 的圆头上有两道弧，但**不并排放大看是会漏掉的**，所以判据用剖面。

## 2. 一条附带的、会影响组件库的事：决策四拿不到多尺度模糊

同一条测法量「条纹还剩多少」（背景是竖条带，所以沿 x 的亮度标准差就是
条纹的残余对比度），按离玻璃上沿的深度扫：

| 离上沿 | 自绘三级多尺度 | over-blur（原生单级 σ=10） | 原生 only |
|---|---:|---:|---:|
| 2.7 逻辑px | 12.4 | 18.0 | 18.0 |
| 6.7 逻辑px | 15.1 | 16.6 | 18.0 |
| 13.3 逻辑px | 15.2 | 18.8 | 17.8 |
| 26.7 逻辑px | 9.1 | 18.6 | 17.4 |
| 40.0 逻辑px（体部） | **4.9** | 18.6 | 17.4 |

玻璃外的背景是 29.9。

原生那条**从边到心是一个常数**（σ 只有一档），自绘三级那条从边缘的 15 掉到
体部的 4.9——差 3 倍。也就是说：

> **决策四的组合（原生模糊 + 自绘折射）与 Phase 2 的多尺度模糊是互斥的。**
> 要「边缘清楚、体部糊」，模糊就必须自己画。

这不推翻决策四，但把 ADR 决策五那张质量表的含义改了：High 档如果定成
「原生模糊 + 自绘折射」，那它就**没有**多尺度。两者只能选一个，写进 ADR。

## 3. 多尺度模糊：它不是「省钱」，是单级做不到

金字塔：第 0 级降到 1/4 边长、σ 用 σ/4；之后每级边长再减半、σ 固定 2.0。
等效 σ 按方差相加，σ=10 时四级依次 **10 / 18.9 / 37.0 / 73.7** 逻辑像素。
shader 侧按深度在**第 0 级与最后一级**之间插值，深度由 `thickness` 控制。

两件事值得记下来：

1. **边缘必须采细级**，不是为了省。折射靠的是背板里的高频细节沿法线错位，
   粗级已经把那些细节糊没了，边缘再采粗级的话折射只剩一道颜色差。所以
   「边缘清楚 + 体部糊」这个组合**单级拿不到**——σ 调大则边缘的折射没了，
   σ 调小则体部不糊。这是多尺度在这里的真正理由。
2. **`thickness` 第一次有了语义。** #130 的参数表只给了名字。Phase 2 把它
   定义成「从细级过渡到粗级的深度」：越厚，重模糊那档越往边缘逼近。
   选这个含义是因为它正好接上唯一一个需要按深度插值的效果，不必新立参数。
   **这是本轮的取舍，不是 #130 的原意**，待 ADR-016 确认。

代价见 §5：三级比单级只贵 **0.19 ms**。

## 4. 动态高光：第一版把基础 glint 替换掉了

写法一上来是「`u_specular_sharpness > 0` 就画方向性高光，否则画静态 glint」。
跑出来两个毛病，同一个根因：

- 朝光那一小段之外，**整圈 glint 全没了**——比 Phase 1 还暗；
- 四个光源角度之间量出来的亮度差只有 **1~2 个灰阶**，等于「动态」看不出来。

根因是把「加在基础上的一层」写成了「替换基础的一层」，外加集中度填了 32
（`pow(N·L, 32)` 掉到一半对应偏离约 10°，在 80px 高的胶囊上只有几个像素）。
改法两条：基础 glint 两档都画，方向项**加**在它上面；方向项铺在折射带
（15px）而不是 4px 的 glint 带上——厚玻璃的边缘高光铺在整条斜面上，挤进最外
两像素里本来就看不见。集中度改 8（约 56° 的弧）。

判据：沿边缘内侧 6 逻辑px 的等距线采一圈，每 15° 一个点，四个钉死的光源角
各一张图，**减掉「同一方位在其余三档的均值」**以消掉背景差异：

| 光源角 | 最亮方位 | 比其余三档高 |
|---|---|---|
| 0° | 0° | +13.1 灰阶 |
| 90° | 30° | +18.0 灰阶 |
| 180° | 180° | +17.2 灰阶 |
| 270° | 240° | +19.2 灰阶 |

**90° 和 270° 的「最亮方位」不等于光源角，这不是 bug。** 胶囊的直段上法线
处处是 `(0, ±1)`，整条上沿（方位约 10°..170°）被均匀照亮，最亮点落在哪儿
只取决于那一段背景本身哪里亮。只有圆头上法线才随方位转，所以 0° / 180°
精确命中。

> 这条换成组件库的话是：**方向性高光在圆角矩形与胶囊上会整条边一起亮，
> 只有圆角处才有「光斑」。** 想要真正的点状高光，形状得有曲率——或者改用
> 别的高光模型。#224 排组件时会碰到。

顶边常驻高光（`top_highlight`）单独一项、与光源方向无关：真玻璃的上沿总比
下沿亮一道（天光），并进方向项的话光源转到下方时顶边会全黑。

## 5. 代价：七档，顺带把 Phase 1 的数字第三次交叉验证了

`./android-measure.sh`，Adreno 740 / 120Hz / 每档 12 秒窗口 / 面板七档全是
120Hz。读的是 `/sys/class/kgsl/kgsl-3d0/gpubusy`，方法与其坑见第二轮 §3.3。

| 档 | GPU 忙 | 折算每帧 | 相对上一档 |
|---|---:|---:|---|
| noblur（地板，连原生模糊都关） | 24.1% | 2.00 ms | — |
| native（只有原生 `backdrop-blur`） | 31.1% | 2.59 ms | 原生模糊 **+0.59 ms** |
| gl-overblur（原生模糊 + 自绘折射） | 34.0% | 2.83 ms | 自绘折射层 **+0.24 ms** |
| gl-base（原生 + 自绘但不模糊） | 35.9% | 2.99 ms | 见下 |
| gl-p0（原生 + 自绘单级模糊） | 56.3% | 4.69 ms | 自绘模糊 **+1.70 ms** |
| gl-merge（两个形状 + 融合） | 57.5% | 4.79 ms | 融合 **≈0** |
| gl-phase2（原生 + 自绘三级多尺度） | 58.6% | 4.88 ms | 多加两级 **+0.19 ms** |

和第三轮的账对上了：原生模糊 0.65 → 0.59（第二轮独立量的是 0.64），自绘
单级模糊 1.71 → **1.70**。**这是第三次用同一套测法量到同一个数。**

本轮新增的三条：

- **多尺度再加两级只要 0.19 ms**，比按「每级 1/4 像素」推算的还便宜。
  原因是第 0 级那 1.70 ms 里大头是**带 3σ 边距的全分辨率拷贝 + 降采样**，
  而后面几级只读很小的纹理，不再付那一笔。
- **融合没有量到额外代价**（4.79 vs 单形状的 4.88 ms）。但两档的玻璃面积
  并不严格相同：融合那档要给圆让出宽度，主胶囊相应缩窄了约 3%。所以只能
  说「没量到」，**不能说「严格为零」**——它和「贵 3% 但面积小 3%」在这组
  数字里分不开。
- **决策四的组合总共 2.83 ms**，比全自绘的 4.88 ms 便宜 **2.05 ms**，
  也就是 Phase 2 全套那一帧的 42%。代价是没有多尺度（§2）。

`gl-base` 比 `gl-overblur` 贵 0.16 ms，差的不是自绘层：`over-blur` 档下
原生那条是 `blur-only`，**连 22px 的 drop-shadow 一起省掉了**。

显存（`dumpsys meminfo` 的 Graphics 行，KB）：地板 56424 → native 61528 →
gl-p0 63696 → gl-phase2 64188。自绘单级比原生多 **2.17 MB**（第三轮量的是
1.87 MB，理论 1.91 MB）；多尺度那两级**实测 +0.48 MB，而按纹理尺寸算只有
65 KB**。对不上，不要据此下结论——这一行包含 surface 与驱动自己的分配，
**0.5 MB 这个量级低于这套测法的分辨率**。

## 6. 顺带修掉两个 Phase 1 的静默错误

都是「不报错、画面看着正常、但确实是错的」那一类。

### 6.1 背板边距只算了 3σ，没算折射

折射把采样点沿法线推出矩形最多 `refraction_strength`（7 逻辑px），而边距
只按 `3σ` 算。于是 **σ=0 的 baseline 档边距是 0**，外缘那 7px 一直在采
clamp 值。三轮都没看出来，因为症状只是「边上一圈颜色发直」。

决策四那两档（模糊归原生、自绘 σ=0）会把它放大成一圈硬边——也就是说，
不修它的话这一轮的结论会是假的。改成 `max(3σ, 折射强度)`。

### 6.2 GL 状态存档放在了背板拷贝之后

拷贝本身要 `bind_texture`，于是存下来的「原纹理」其实是我们自己那张背板，
复原等于把渲染器的绑定换成了我们的。Skia 的 `GrDirectContext` 自己缓存了
一份 GL 状态的影子，这种错的症状是**下一帧画面错乱而不是报错**。挪到
`draw()` 最前面，并且三个纹理单元（清晰背板 / 细级 / 粗级）都存。

### 6.3 另两条是工具侧的

- **`.NET` 的「当前目录」和 PowerShell 的 `Set-Location` 不是一回事。**
  `GetFullPath` 用前者，于是 `shot.ps1 -Out shots/x.png` 会把文件静默写到
  宿主进程的起始目录下——实测写出过 `shots/shots/*.png`，而脚本照常打印
  「已写」。
- **融合间距与光源角必须钉得住。** 两者原本都由动画相位决定，而相位取决于
  「窗口起来之后 Timer 跑了多久」，那段启动耗时每次不一样：三张本该是不同
  间距的截图，量出来是 125 / 75 / 150px，和预期全对不上。加了
  `GLASS_MERGE_GAP` / `GLASS_GL_LIGHT` 钉死，背景也能用 `GLASS_TICK=10000`
  冻住。**这是第一轮「GLASS_COUNT=10 只画 6 条」的同一个形状**：
  档位不在画面上、也不可复跑，记录里的数字就是碰运气来的。

另有一条只在窄屏上成立的：融合那一档的第二个形状原本摆在胶囊左边，而手机
宽度只有 406 逻辑px、胶囊自己就占 358，圆被推到 `x = -68` **直接出界**——
画面上看起来像「第二个形状没画出来」，而 logcat 里形状数照样是 2。现在
那一档会给圆预留宽度并把并集整体居中。

## 8. 这一轮没做的

- **环境色自适应（P2）没做**，#130 正文就把它排在 P2，不属于 Phase 2。
- **按压/拖动形变（P1）没做。** 融合做了，形变没做——它要手势，而这个
  实验台连输入都没接。排 #224。
- **Apple 两端仍然没验。** 第三轮推断那条路大概率不通（Metal via wgpu，
  notifier 拿不到渲染目标），本轮没有新信息。仍排在 #225 最前面，
  **它决定玻璃是一套还是两套**。
- **低端机、功耗温度、滚动残影**全都还没碰，同第三轮，转 #225 / #226。
  本轮七档各只跑了 12 秒，热降频来不及发生。
- **与 Flutter 版并排对照**已于 2026-11-25 移出 #130 范围（仓库所有者定：
  观感一致性由人用眼睛判，不作为产出项）。
- **`GlassPreset` 那五个预设仍然是猜的。** #130 只给了名字没给参数；本轮
  只是把新字段按同一思路填了进去，没有任何观感验证。等 #224。
