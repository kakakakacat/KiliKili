# QA-001：端到端功能矩阵与发布前清单

状态：**测试方案，待按候选版本执行**
关联：[RFC-0001 §8–9](../architecture/RFC-0001-rust-slint-migration.md)、[验证能力矩阵](../m0/VALIDATION-CAPABILITY.md)、[M0 基线](../m0/BASELINE.md)、[Issue #13](https://github.com/kakakakacat/KiliKili/issues/13)

本文规定如何验收一个发布候选版本，不代表这些场景已经通过。每次发布复制文末记录模板，填写版本、设备、结果和证据链接。`PASS` 必须有实际操作结果；无法执行时记 `BLOCKED` 或 `NOT TESTED`，不可用构建成功代替运行时通过。

## 1. 执行约定

- 使用同一候选 commit 构建的 **Release 产物**。记录 commit、版本号、产物哈希、平台、系统版本、设备型号、安装方式、测试账号类型和执行时间。日志与截图须删除 Cookie、token、手机号、设备标识、视频和用户的私人信息。
- 准备匿名态、普通登录态各一套；涉及账号的场景只用可控制的测试账号和内容。准备一条可公开播放、含弹幕和评论的固定 UGC 视频，并记录其清晰度、时长及是否 DASH 分轨。样本失效时记录替代样本及原因。
- 功能用真实设备执行。Android、iOS、macOS、Windows 的可用性及 iOS 签名前置条件见[验证能力矩阵](../m0/VALIDATION-CAPABILITY.md)。Linux 当前只有构建与静态产物检查，GUI 验收记 `NOT TESTED`，不能写作通过。
- 对每条用例记录 `PASS / FAIL / BLOCKED / NOT TESTED`、执行人、设备、步骤中的实际结果、截图或脱敏日志、缺陷链接。`BLOCKED` 用于环境或外部服务阻断；`FAIL` 用于已观察到产品行为不符。修复后重测原场景及关联场景。
- **P0** 是发布硬门槛：任一目标平台的 P0 `FAIL` 或 `NOT TESTED`，不得宣称该平台验收通过。`BLOCKED` 需写明原因、替代证据和发布决策人；不能自动视为通过。P1 缺陷需要明确处置结论。平台未计划发布时标注 `N/A` 和理由。

## 2. 功能矩阵

所有目标平台至少跑匿名主链路。登录、后台、触摸与桌面交互按平台能力执行；同一用例在不同平台要分别记录结果。步骤以当前 Flutter 客户端为准，Phase 2 更换 UI 后沿用行为目标并更新入口名称。

| F13 | P1 | 评论/搜索/详情在弱网、空结果和服务端错误下操作 | 显示可理解的状态与重试入口；返回导航仍可用；错误不被误报为成功 |

**F07 与 F12 为什么必须真机**：进度游标的判据（`bili_danmaku::cursor`）由 Rust
单测与 `test/bridge/danmaku_bridge_test.dart` 钉住，但它的**输入**——播放器在
回前台时吐出的那串 position——只有真实播放器才会产生。CI 全绿只说明「给定这串
进度，判得对」，不说明真机上那串进度长什么样。issue #89 就是这么漏过去的。

**F11 的数据边界**：当前 `GStorage.exportAllSettings()` 只包含 `setting` 与 `video` 两个 box，不能作为账号、`historyWord`、`watchProgress` 的完整备份。升级测试要使用可恢复的测试设备或独立副本，先留好旧版数据和回退包；不得在唯一的真实用户数据上试验。相关代码见 `lib/utils/storage.dart`。

### 2.1 typed 直连迁移的待确认项

ADR-011 决策五把对照机制定为「Rust 冻结快照 + Dart parity 测试」。两者**只能证明 Rust 与迁移前的 Dart 行为一致**，前提是 fixture 反映真实响应。部分接口匿名取不到（要登录态）或拿不到可用的入参，其 fixture 是**手工构造**的：它证明映射自洽，不证明我们对协议的理解正确。这些路径必须在发布前用真机各走一遍，CI 全绿不能替代。

| M02 | P1 | 评论区开关状态、表情包面板（S1 #51） | 要登录态（匿名分别是 `code -101` 与 `packages: null`） | 用 UP 主账号打开自己稿件的「评论精选/关闭评论」菜单；在评论框打开表情面板，各组图标与文字表情都能插入 |

### 2.2 封面大卡片的人工验证（issue #108）

视频卡片统一为 `CoverScrimCard`：#108 时文案叠在封面底部，#295 起「UP 名 +
标题」移到封面**下方**（最多两行，日期和操作按钮在右下角），封面底部只留
一条放辅助信息的矮遮罩，配色由 `bili_core::cover_scrim` 按封面取色算出。Rust 单测钉住的是「给定一张缩略图，算出的对比度达标」；
**它不保证屏幕上好看、也不保证取到的是那张封面**——缩略图由宿主解码，
解码失败、封面换了、滚动复用卡片都只有真机能验。

| Linux | 构建、解包、原生库与依赖检查；功能项记 `NOT TESTED` | 目前无可用 Linux GUI/硬解验收环境，按 best-effort 发布范围单独披露 |

自动检查由 `ci.yml` 触发：PR、main 的 push、每日定时和手动运行都会跑。**2026-11-12 到 2026-11-27 之间 PR 上曾暂停**（重构期，issue #114），2026-11-28 起 ruleset「main regression gate」重新把 `regression gate` 设成必需检查，下文「每个 PR」重新成立；发布候选仍须确认记录的那次 run 对应的正是候选 commit，必要时以 `workflow_dispatch` 重跑。每次运行都会跑 `rust.yml`（Rust 检查与冻结快照）、`flutter-test.yml`（Dart 基线对照与真实 FFI）、Android Release 开发包构建及 `libbridge_flutter.so` 产物检查；`regression gate` 要求这些 job 全部成功。每日定时运行还会调用 iOS、macOS、Windows、Linux 的既有打包 workflow；手动运行 CI 时可用 `full_platforms` 请求相同的全平台构建。分支保护（ruleset「main regression gate」）的 `enforcement` 为 `active`，`bypass_actors` 为空：gate 报不上来时谁都没有豁免，唯一的出路是把它改回 `disabled`。CI 的固定 fixture 对照不访问上游实时接口，基线版本见 [M0 基线](../m0/BASELINE.md)；更新快照须在 PR 中审查差异并重跑 Dart parity，不得在 CI 中设置 `UPDATE_GOLDEN`。

自动构建仍只证明产物可打包；它不能验收视频首帧、硬解、PiP、后台音频或升级后的真实用户数据。每个发布候选仍须填入 workflow run 链接、真机执行记录，并对目标平台的最终产物运行 `python3 tool/inspect-artifact.py <artifact> --require <原生库文件名>`。实际库名按平台产物确定，不能只看构建日志或包体积。产物检查方法见[发布产物复盘](../m0/2026-11-10-RELEASE-REVIEW.md)。

## 4. 性能采样场景

本节定义采样方法，**不预填基线数值**。同一平台只比较同一台设备上的旧版基线和候选版：固定系统版本、刷新率、电源/充电状态、亮度、音量、网络、视频样本、清晰度、弹幕设置与账号状态；记录工具版本和环境温度。先预热一次，再交替采样旧版与候选版各至少 5 次，保存每次原始值及 p50/p95；样本不足以稳定估计 p95 时同时列出最大值，不把单次波动当作结论。测试中改变条件必须重采双方。

| ID | 指标 | 固定操作及记录值 | 判定方式 |
|---|---|---|---|
| P01 | 冷启动 | 杀进程后点击图标至首页可交互；记录每次毫秒数、p50/p95 | 与同设备旧版相比；退化需定位原因，不用 CI runner 数据 |
| P02 | 内存 | 空闲首页、长列表滚动 5 分钟、1080p 播放 10 分钟；记录 RSS/PSS、GPU 内存、峰值及结束值 | 不持续增长；峰值差异有解释 |
| P03 | CPU | 固定 1080p 视频与弹幕密度，稳态播放 10 分钟；记录平均/峰值和硬解状态 | 与同设备基线比较，记录软/硬解变化 |
| P04 | 帧耗时 | 首页快速滚动及视频弹幕各 2 分钟；记录 p95/p99、丢帧数、设备刷新率。**刷新率必须在滚动当中取**——多数 Android 面板触摸时才升到高刷，滑动前后读到的都是休息档；`dumpsys SurfaceFlinger --latency` 的环形缓冲只存 128 帧（120 Hz 下约 1 秒），要分段取样再按时间戳去重合并 | 依据实际刷新率解释预算与退化，不混合不同刷新率设备。**debug（JIT）包的帧数据一律作废**，只认 profile/release 的 AOT 包 |
| P05 | Seek 延迟 | 同一视频固定目标位置，前跳/后跳各 5 次；从操作到有效新画面计时 | 记录每次值与失败次数；与基线比较 |
| P06 | 网络恢复 | 固定弱网、断线 30 秒、恢复；记录超时、重试次数、首帧恢复时间和请求数 | 无无限重试或请求风暴；功能行为同时满足 F10 |
| P07 | 电量/能耗 | 同亮度音量和网络播放同一 1080p 视频 30 分钟；记录电量变化及系统能耗工具数据 | 同设备 A/B 比较；温度或后台负载异常时重测 |
| P08 | 安装体积 | 对同架构 Release 产物记录字节数、内含原生库及相对上版增量 | 每次增量有原因；构建/产物检查通过 |
| P09 | 首页底栏响应（#127） | 三种底栏分别在动画开/关下，测相邻及跨两项切换，区分首次进入与再次切换；固定页面数据和网络，记录点击到选中态、目标页构建、首帧及转场完成的原始耗时。用 profile/release 帧时间线分开 UI、Raster 与玻璃背板开销，并检查初始化、请求和图片解码 | 关闭动画时不应有固定转场等待或途经页初始化；开启时不把有意的转场时长算作首帧阻塞。与同设备旧版重复比较；Widget 测试只证明切换行为，不能充当真机耗时基线 |

P09 可用 `tool/navigation_profile/README.md` 的独立 profile 包记录回调与帧时间；边界和原始记录示例见 [#127 未登录采样](measurements/nav-127-anonymous-2026-11-26/README.md)及 [登录态采样](measurements/nav-127-authenticated-2026-11-26/README.md)。两种状态各保留 30 条有效样本，覆盖悬浮底栏、动画关闭；其他样式和旧版对照仍待测。

性能门槛采用 [RFC-0001 §8.1](../architecture/RFC-0001-rust-slint-migration.md) 的原则：冷启动、CPU、Seek 不劣于同设备基线；内存无持续增长；包体增量可解释。尚无数值基线时先记录 `NO BASELINE`，不得填写 `PASS` 或声称性能改善。硬解、PiP、后台行为与渲染性能不能由虚拟化 CI runner 验收。

### 发布包签名的人工验证（#121）

CI 已经在打包时签名并当场复核一遍（`linux_x64.yml` 的「校验签名」、
`win_x64.yml` 的 `signtool verify`、`mac.yml` 的 `stapler validate` 与
`spctl`）。**CI 验的是「我刚签的东西签住了」，验不了下面这三件事**，它们
只能在真实系统上做一次：

| ID | 优先级 | 平台 | 操作与通过标准 |
|---|---|---|---|
| S01 | P0 | 全部 | 从 Release 页**按用户的路径**下载产物，按[发布签名](../release/SIGNING.md) §7 验一遍；指纹/证书主体与该文 §2.5、§3.4、§4.4 的记录表逐字一致。只看验证工具说「通过」不够——换一把钥匙签也会通过 |
| S02 | P0 | Android / Linux / Windows / macOS | **同身份原地升级**：用上一个正式版安装，再用候选版覆盖安装，不得要求先卸载，设置与登录态保留。这正是「身份可复用」的唯一硬证据，签名验过不等于升级路径通 |
| S03 | P0 | macOS / Windows | 在**没装过开发工具的干净系统**上双击打开：macOS 不应出现「无法验证开发者」；Windows SmartScreen 的拦截框如仍出现，记录下来并在发布说明里说明。开发机上装过证书会让这一条假通过 |
| S04 | P1 | Linux | `rpm --checksig`（导入公钥后）与 `dnf install` 本地包不报签名错误。AppImage 没有包内签名（`appimagetool --sign` 会把包截断，见 [发布签名](../release/SIGNING.md) §2.1），只验 `.asc` |
| S05 | P0 | Android 验证包（#146） | 同一架构、连续两次 CI 构建的 `.dev` APK，在同一设备依次安装，第二次覆盖成功且设置、登录态、离线缓存仍在；记录两个 run、APK 哈希、应用 ID 和证书 SHA-256。首次测试不得用历史临时 debug 签名包作起点 |

未签名的平台把对应行记 `N/A` 并写明原因（iOS 的理由见 SIGNING.md §5），
不要记 `PASS`。

## Player Port 接入后的必验路径（#4）

同一候选构建上连续快速切视频、连发前后 Seek、Seek 尚未完成时退出页面，

## Android 打开 Impeller 后的必验路径（#230）

Android 侧 `EnableImpeller` 由关改开（`android/app/src/main/AndroidManifest.xml`）。
渲染后端换了，**所有经过 GPU 的路径都要重验一遍**，而且不能只看包名或分支名：

- **先确认后端**。`adb logcat` 里 `Using the Impeller rendering backend (Vulkan)`
  才算开，`[Action Required]: Impeller opt-out deprecated` 是仍然关着。
  装包、切分支、合并都可能让实际跑的东西和预期不一致，每轮都读一次。
- **玻璃导航栏**：三种首页底栏的胶囊背景应与 iOS 观感一致（折射而非模糊）。
  `ImageFilter.isShaderFilterSupported` 只在 Impeller 下为 true，这是
  `lib/common/widgets/floating_navigation_bar.dart` 走 shader 还是回退
  `ImageFilter.blur` 的分水岭。
- **播放器 Texture 通道**：播放、全屏切换、后台切回；确认仍是硬解
  （`dumpsys media.player` 或 logcat 的解码器名）。
- **弹幕**：彩色、描边、密集并发下的叠加与清屏。**这是目前唯一量到 Impeller
  更差的场景**：在 120 Hz 面板上播放高密度弹幕视频（约 5.6 万条 / 4 分 18 秒），
  Skia 每一帧都踩在 8.33 ms 上（有效 120.7 fps，GPU 40%），Impeller 有 46% 的
  帧要两个 vsync（有效 82.6 fps，GPU 61%），重复一轮复现。没有出现超过
  2.5 个周期的重掉帧。**换到 60 Hz 面板上两者都够**，这个差距只在高刷设备上看得见。
- **PiP 与纹理销毁重建**：与 [Player Port 一节](#player-port-接入后的必验路径4) 同一组操作。
  （#230 本轮已验：开「后台画中画」后按 HOME 进小窗，画面与弹幕都在，不黑屏、
  不倒置；`am start` 回前台后纹理正常恢复。）
- **帧耗时与 GPU 开销**：按 §4 P04 采样。两个场景的结论**方向相反**，必须分开记：
  首页滚动是掉帧率 14.4% → 3.1%（GPU 37.6% → 65.5%），高密度弹幕是
  120.7 → 82.6 fps（GPU 40% → 61%）。两处 GPU 都涨到约 1.6 倍，PSS +11%。
  **这个代价在低端机上是否吃得下，没有数据。**
- **GLES 回退**：Vulkan 不可用时 Impeller 走 GLES。**不需要低端设备也能验**：
  临时在 manifest 里加
  `<meta-data android:name="io.flutter.embedding.android.ImpellerBackend"
  android:value="opengles" />` 打一个包，任何 Vulkan 机器都会被逼到 GLES 后端，
  logcat 会打 `Using the Impeller rendering backend (OpenGLES)`。
  **这条路第一次跑就抓到一个 bug**（玻璃导航栏上下倒置，见 #230），所以它
  必须每次都验，不能靠「Vulkan 没问题所以 GLES 也没问题」推断。
  仍未覆盖的是**真实低端/老设备的性能**，那是硬件问题，不是这条代码路径。

验证记录见 issue #230。另有一个与本改动无关、但在这类真机验证里会咬人的坑：
`flutter build apk --profile` 产出的 applicationId 与正式包同名
（`android/app/build.gradle.kts` 只给 `debug` 和 `.dev` 加了后缀），
装到带正式版的设备上会覆盖用户数据；装之前先 `aapt2 dump packagename` 核一遍。
